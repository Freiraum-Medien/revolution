# Revolution – Entwicklung

Mail-Client für GNOME (GTK4, libadwaita, Blueprint, Evolution-Data-Server 3.56). App-ID `de.freiraum_medien.Revolution`, Entwicklungsvariante `de.freiraum_medien.Revolution.Devel`.

## Build und Test

Voraussetzungen (Ubuntu 26.04): meson, ninja, blueprint-compiler, gettext, gtk4 ≥ 4.22, libadwaita-1 ≥ 1.9, camel-1.2, libedataserver-1.2, libebook-1.2 und libecal-2.0 ≥ 3.56, fribidi, webkitgtk-6.0 ≥ 2.52, appstreamcli, desktop-file-validate, glib-compile-schemas. Pakete:

```sh
sudo apt install meson ninja-build blueprint-compiler gettext libgtk-4-dev libadwaita-1-dev \
  libcamel1.2-dev libedataserver1.2-dev libebook1.2-dev libecal2.0-dev libfribidi-dev libwebkitgtk-6.0-dev \
  appstream desktop-file-utils libglib2.0-bin
```

Einrichten und bauen:

```sh
meson setup build                                             # Profil default (Release)
meson setup build-devel -Dprofile=development -Dwerror=true   # Entwicklungsvariante, für alle Tests
meson compile -C build-devel
```

Profile (#439): Tests und Testläufe nutzen die Entwicklungsvariante in `build-devel/` (Standard `BUILD` aller Skripte in `tests/` und `scripts/screenshot.sh`, ebenso der Git-Hook), damit eine installierte Revolution (`de.freiraum_medien.Revolution`) daneben laufen darf. Die Skripte lesen App-ID (`BUILD/data/*.metainfo.xml`) und Datenordner (`USER_DIR_NAME` in `BUILD/config.h`) aus dem Build und prüfen `NameHasOwner` nur für diese App-ID.

| | Release (`profile=default`) | Devel (`profile=development`) |
|---|---|---|
| App-ID, Bus-Name | `de.freiraum_medien.Revolution` | `de.freiraum_medien.Revolution.Devel` |
| Daten, Cache | `~/.local/share/revolution`, `~/.cache/revolution` | `~/.local/share/revolution-devel`, `~/.cache/revolution-devel` |
| Erkennbar | Symbol `de.freiraum_medien.Revolution` | Stilklasse `devel` (gestreifte Kopfleiste, wie Stamp stamp-window.c:224-225), Symbol `….Devel` |
| GSettings | Schema `de.freiraum_medien.Revolution` | dasselbe Schema (wie GNOME Calendar); Tests laufen mit `GSETTINGS_BACKEND=memory` |

Die Testkonten-Datei `~/.config/revolution/testkonten.ini` gilt für beide Profile. Bisherige Ordner `build/`, `build-hook/`, `build-check/` (Release) bleiben nutzbar, Testskripte dann mit `BUILD=build`.

Installieren für den eigenen Benutzer (Freigabe Arnd 28.10.2026, #366; nötig für Benachrichtigungen, siehe unten): Programm `~/.local/bin/revolution`, Desktop-Datei `~/.local/share/applications/de.freiraum_medien.Revolution.desktop`, Schema in `~/.local/share/glib-2.0/schemas` (kompiliert `meson install`), Entfernen `ninja -C build-install uninstall`. Anleitung: `~/Dokumente/Privat/ubuntu/revolution.md`.

```sh
meson setup build-install --prefix ~/.local
meson install -C build-install
```

Tests (Desktop-Datei, Metainfo mit `appstreamcli validate --no-net`, GSettings-Schema):

```sh
meson test -C build-devel
```

### Smoke-Test (#349)

Gegen die echten Konten aus GNOME Online Accounts, daher eigene Suite `smoke`, die `meson test` ohne `--suite` auslässt (`add_test_setup` in `meson.build`):

```sh
meson test -C build-devel --suite smoke -v      # oder: tests/smoke.sh [AUSGABEORDNER]
```

Vorbedingungen: Netz, Konten in GOA, echter Session-Bus, die App-ID des Builds läuft nicht (`NameHasOwner` = false; die installierte `de.freiraum_medien.Revolution` darf laufen, #439), Pakete wie unter Screenshots. Ohne `meson test` baut das Skript vorher selbst unter `flock` (`BUILD_LOCK`, Standard `BUILD/.build.lock`; gemeinsame Sperre aller Agenten `App/build/.build.lock` ausdrücklich setzen). Ausgaben (Logs, PNGs, Vergleichslisten) nach `build-devel/smoke/` bzw. in den Ordner aus Argument oder `SMOKE_OUT`; Zeitlimit je Start `SMOKE_TIMEOUT` (Standard 120 s).

Ablauf: vier App-Starts über `scripts/screenshot.sh` (Mail hell und dunkel in 1200×4800 mit allen Konten und Ordnern, Kalender mit Strg+2, Kontakte mit Strg+3) mit `G_MESSAGES_DEBUG=revolution` und `G_DEBUG=fatal-criticals`. Je Start wartet das Skript, bis jedes angezeigte Konto fertig ist (Log `Ordner: <UID> <N> geladen` bzw. Fehlerzeile), nimmt den Screenshot auf und schließt das Fenster per `WM_DELETE_WINDOW`. Geprüft wird je Start:

- (a) Konten: angezeigte Konten = Regel aus `src/mail/mail-account.c`, unabhängig per Python-GI gegen die Registry ausgewertet
- (b) Anmeldung: je Konto `angemeldet: <UID> … angenommen`
- (c) Ordner: Log `Ordner: <UID> <Name>` und Anzahl = `tests/testdaten.py --ordner` (nur lesend)
- (d) Log: Positivliste, nur DEBUG-Zeilen der App; ausgenommen zwei feste `libEGL warning: …DRI3…`-Zeilen von Mesa unter Xvfb, jede andere Zeile ist ein Fehler
- (e) Beenden: Exit 0, kein Rest-Prozess (App, Xvfb, Compositing-Attrappe), App-ID nicht mehr auf dem Bus

Am Ende (f): PIDs von `evolution-source-registry` und `goa-daemon` sowie sha256, Änderungszeit und Inode jeder Datei in `~/.config/evolution/sources` unverändert. Je Prüfung eine Zeile `OK …` bzw. `FEHLER …`, Exit 0 nur ohne Fehler. Gegenprobe ohne Netz (Bus bleibt erreichbar): `unshare -n --map-current-user tests/smoke.sh` meldet FEHLER und Exit 1.

Abbrüche (#411, alle Testskripte in `tests/` über `tests/abbruch.sh`): Jeder Abbruch eines Teilschritts zählt als `FEHLER  Abbruch: …` und ergibt Exit ≠ 0, auch wenn er in einer Pipe oder `$(…)` passiert: Exit ≠ 0 von `tests/testdaten.py` (Traceback, `ABBRUCH`), Exit ≠ 0 eines Treibers ohne eigene FEHLER-Zeile (die Treiber melden eine Ausnahme selbst als `FEHLER … Abbruch`), Zeitlimit. Zeitlimits: `TD_TIMEOUT` je Aufruf von `testdaten.py` (Standard 300 s), `LAUF_TIMEOUT` je Treiber-Lauf, App-Starts über `scripts/screenshot.sh` mit Wartezeit + 120 s. Einen transienten Netzabbruch (z. B. Gmail `imaplib.IMAP4.abort: socket error: EOF`) wiederholt `testdaten.py` einmal, außer beim Versand und bei `--server … neu`; jede Wiederholung steht als `WERT` am Ende des Skripts.

Starten aus dem Build-Ordner: Das Schema liegt kompiliert in `build-devel/data`. Einstellungen nur im Speicher (`GSETTINGS_BACKEND=memory`): beide Profile nutzen dasselbe Schema, ohne memory schriebe die Entwicklungsvariante in die dconf-Einstellungen der installierten App (#439).

```sh
GSETTINGS_SCHEMA_DIR=build-devel/data GSETTINGS_BACKEND=memory build-devel/src/revolution
```

Headless-Start ohne Fenster auf dem Desktop (Anzeige nur Xvfb, X11 erzwungen):

```sh
env -u WAYLAND_DISPLAY GDK_BACKEND=x11 GSETTINGS_SCHEMA_DIR=build-devel/data GSETTINGS_BACKEND=memory \
  xvfb-run -a build-devel/src/revolution
```

Der Start nutzt den echten Session-Bus, keine eigene `dbus-run-session`. Eine eigene Sitzung startete eine zweite `evolution-source-registry` und einen zweiten `goa-daemon` gegen das echte `~/.config`; die zweite Registry schrieb Dateien in `~/.config/evolution/sources` neu (#343). Vorher prüfen, dass Revolution nicht schon läuft, sonst öffnet der Start ein Fenster in der laufenden Instanz auf dem Desktop: `gdbus call --session -d org.freedesktop.DBus -o /org/freedesktop/DBus -m org.freedesktop.DBus.NameHasOwner de.freiraum_medien.Revolution` muss `(false,)` liefern.

## Architektur

Muster, keine Hilfsbibliothek (CLAUDE.md Architektur-Festlegungen 1–6). Beispiel im Code: `src/main.c` (#343).

**Worker:** Jeder Camel-/EDS-Aufruf läuft per `GTask` im Worker-Thread, nie im UI-Thread. Der `*_sync`-Aufruf steht in der Thread-Funktion, das Ergebnis kommt im Rückruf im UI-Thread an. Nur dort werden Widgets und Modelle geändert. Vorlage: Evolution `e_mail_session_get_inbox` (libemail-engine/e-mail-session.c:2538-2618). Ausnahme (#345): reine Lesezugriffe der `ESourceRegistry` auf ihre Quellen im Speicher (`e_source_registry_list_sources`, `_ref_source`, `_find_extension`) sind im UI-Thread zulässig; sie lesen eine Hashtabelle unter Mutex, ohne D-Bus (EDS e-source-registry.c:459-472, 2432-2439, 2465-2492, 2576-2600). Evolution macht es ebenso (e-mail-account-store.c:1216-1225). Alles mit D-Bus, Netz oder Datei bleibt im Worker.

```c
static void
load_registry_thread (GTask *task, gpointer source, gpointer data, GCancellable *cancellable)
{
  GError *error = NULL;
  ESourceRegistry *registry = e_source_registry_new_sync (cancellable, &error);

  if (registry == NULL)
    g_task_return_error (task, error);
  else
    g_task_return_pointer (task, registry, g_object_unref);
}

/* Aufruf im UI-Thread; on_registry_loaded läuft wieder im UI-Thread. */
task = g_task_new (app, cancellable, on_registry_loaded, user_data);
g_task_run_in_thread (task, load_registry_thread);
```

Die `ESourceRegistry` wird beim Start so geladen und an der Anwendung gehalten (`g_object_get_data (app, "registry")`). Ihre Signale kommen trotzdem im UI-Thread an: EDS merkt sich beim Anlegen `g_main_context_ref_thread_default ()` (e-source-registry.c:1726), und das ist im GTask-Worker der globale Standard-Kontext. Beleg im Log: `G_MESSAGES_DEBUG=revolution` zeigt Worker- und UI-Thread.

**Datenmodell:** `GListStore` aus konkreten GObject-Items, angezeigt mit `GtkListView`/`GtkColumnView` (Beispiel: Seitenleiste, `src/mail/mail-view.c:359-363`, `mail-view.blp:131`: Konten als `GListStore`, je Konto ein `GtkTreeListModel` über seinen Ordnern (`RevolutionMailFolder`), über `GtkMapListModel` und `GtkFlattenListModel` als Abschnitte mit dem Kontonamen als Kopf, #348). Änderungen am Store (`g_list_store_append`, `g_list_store_splice`) nur im UI-Thread, also im GTask-Rückruf oder in Signalen der Registry (#345). Eine eigene `GListModel`-Klasse erst, wenn ein `GListStore` nicht reicht.

**Camel-Ordner:** Immer über `camel_store_get_folder_sync (store, full_name, …)` holen, nie das Ergebnis von `camel_store_get_inbox_folder_sync` für Anzeige, Flags oder Refresh verwenden. Die Standardversion ruft die vfunc `get_folder_sync` direkt mit „inbox“ und umgeht den Ordner-Cache (EDS camel-store.c:373-388 gegen 1369/1469); imapx überschreibt sie nicht, es entstehen zwei Instanzen. Bei microsoft365 den Posteingang über den Ordnertyp `CAMEL_FOLDER_TYPE_INBOX` finden (camel-m365-store.c:161), nicht über den festen Namen „inbox“ der Standardversion. Evolution macht es ebenso (e-mail-session.c:2763, mail-folder-cache.c:779).

**eds-compat.c:** Die einzige Datei für Aufrufe, die von der EDS-/Camel-Version abhängen (3.56 heute, 3.62 später), jeweils mit `#if EDS_CHECK_VERSION (…)`; sie bricht den Build ab, wenn EDS älter als 3.56 ist. Seit #357 die Thread-API (`camel_folder_thread_messages_new` in 3.56, `camel_folder_thread_new` ab 3.62, der 3.62-Zweig ist hier mangels EDS 3.62 nicht übersetzt). #415: Jeder Abgleich eines Ordners läuft über `revolution_eds_folder_refresh_info_sync`. Bei microsoft365 setzt sie danach `folder_flagged` der Nachrichten zurück, die erst der Abgleich geändert hat (wie EWS und imapx); sonst schickte der nächste Sync (Camel nach `store-changes-interval`, oder eine eigene Bedienung im selben Ordner) die Server-Änderungen als Graph-PATCH zurück, aus Teilobjekten des Deltas mit leeren Kategorien und normaler Wichtigkeit (evolution-ews 3.56.2, camel-m365-folder.c:902-904, 1385-1388). Vorher-Stand, Abgleich, Zurücksetzen und Speichern der Summary laufen unter der Ordnersperre (`camel_folder_lock`); gespeichert wird danach erneut, sonst ginge das Echo nach Beenden oder Absturz kurz nach dem Abgleich beim nächsten Start raus. Restrisiko: eine eigene Flag-Änderung an einer vorher unveränderten Nachricht, die gesetzt wird, solange der Abgleich den Ordner gesperrt hält (inklusive Netz), bleibt nur lokal (das Setzen sperrt nicht, erst das Speichern wartet auf die Sperre). Log: `Abgleich: <UID> <Ordner>: <N> Server-Änderungen nicht zurückgeschrieben`. Filtertreiber gibt es keinen (`get_filter_driver` liefert NULL, keine Regeln), damit auch keinen Sofort-Sync nach neuer Mail. #416: Dasselbe für die beiden anderen Wege, auf denen microsoft365 abgleicht: `revolution_eds_folder_transfer_messages_to_sync` (Verschieben/Kopieren; der Zielordner wird abgeglichen, evolution-ews camel-m365-folder.c:1547-1553) und `revolution_eds_store_get_trash_folder_sync` (Papierkorb; schickt erst alle offenen Ordner und gleicht dann den Papierkorb ab, camel-m365-store.c:1446-1459). Der Papierkorb wird dafür vorher über den Typ in der Ordnerliste geöffnet (`CAMEL_STORE_FOLDER_INFO_FAST`), die anderen offenen Ordner bleiben für die Dauer gesperrt. Beide im Worker und ohne gehaltene Ordnersperre aufrufen; nie `camel_store_get_trash_folder_sync` oder `camel_folder_transfer_messages_to_sync` direkt. Restrisiken: ein Ordner, der zwischen den beiden Listen offener Ordner (`camel_store_dup_opened_folders` in Revolution und in `get_trash`, camel-m365-store.c:1445) geöffnet wird, ist nicht gesperrt und wird ungesperrt synchronisiert; `get_trash` synchronisiert alle offenen Ordner, Flag-Aufträge warten so lange, daher den Papierkorb in #363 nicht bei jedem Löschen neu holen. Test gegen KONTO_M365: `flock build/.run.lock tests/verschieben.sh` (Programm `tests/verschieben.c` ohne Oberfläche, Ausgaben in `build-devel/m5-416/`): je Lauf Einladung in den Papierkorb, Änderung am Server (`tests/testdaten.py --server KONTO markiert Papierkorb`), Papierkorb holen, zurück; Änderung an der Einladung in Revolution-Test, „Anzeige Inline-Bild (cid)“ dorthin und zurück; Prüfung: schreibend nur `POST …/move`, kein PATCH. `ROH=1` ist die Gegenprobe direkt über Camel (Echo-PATCH erwartet), `LAEUFE` (Standard 3).

**Verzeichnisse:** Beim Start werden `~/.local/share/revolution` und `~/.cache/revolution` angelegt (`g_get_user_data_dir ()`/`g_get_user_cache_dir ()` + `USER_DIR_NAME`, Rechte 0700), getrennt von Evolution (`…/evolution`). #439: Die Entwicklungsvariante nutzt `revolution-devel` (`USER_DIR_NAME` in `meson.build`), damit Testläufe die Daten der installierten App nicht berühren; Stamp nutzt für beide Profile „stamp“ (stamp-helper.c:46-58).

**Übersetzungen (#438):** Alle Zeichenketten in `_()`, `C_()`, `N_()`, `ngettext` (C und Blueprint), Desktop-Datei, Metainfo und GSettings-Schema sind Englisch (GNOME-Wortwahl, Begriffe nach Evolution 3.56.2 po/de.po); Deutsch steht nur in `po/de.po`. Neue Zeichenketten immer in beide: Datei mit Zeichenketten in `po/POTFILES.in`, dann `meson compile -C build-devel revolution-pot` (schreibt `po/revolution.pot`, nicht im Repo) und `revolution-update-po`, Übersetzung eintragen, Prüfung `msgfmt --check --statistics -o /dev/null po/de.po` (0 unübersetzt, 0 unscharf). Gleiche englische Wörter mit verschiedener deutscher Übersetzung bekommen einen Kontext (`C_("action", "Archive")` gegen den Ordner „Archive“). Aus dem Build-Ordner gestartet bindet die App die Textdomain an die dort gebauten Übersetzungen (`BUILD/po/<Sprache>/LC_MESSAGES`, `BUILD_LOCALE_DIR` in `meson.build`), sonst an `LOCALEDIR`. Tests: `tests/abbruch.sh` setzt `LC_ALL=de_DE.UTF-8`, die Treiber suchen Bedienelemente über die deutschen Namen. Englisch prüfen: `LC_ALL=C scripts/screenshot.sh NAME prefer-light`.

**Ordner (#348):** Nach der Anmeldung lädt derselbe Worker-GTask je Store die Ordnerliste (`camel_store_get_folder_info_sync`, RECURSIVE|SUBSCRIBED ohne FAST, Begründung in `src/main.c` bei `note_store_thread`); Konten, die die Session zur Laufzeit hinzufügt, laufen über das Signal `services-changed` denselben Weg. Vergleichsliste nur lesend: `tests/testdaten.py --ordner`; App-Log mit `G_MESSAGES_DEBUG=revolution`: `Ordner: <UID> <Name>`. Screenshot aller Ordner: `WAIT=40 scripts/screenshot.sh ordner-hell prefer-light 1200x4800`.

**Spezialordner, Zähler, Erstauswahl (#350):** Gesendet, Entwürfe und Archiv kommen aus der ESource des Kontos (Identität: `sent-folder`, `drafts-folder`; Konto: `archive-folder`), wie Evolution. Zeigt sie nicht in diesen Store (Konten, die Evolution nie eingerichtet hat: `folder://local/…`), gilt das Ergebnis von `camel_store_initial_setup_sync`, nur im Speicher, nie in die ESource geschrieben (`src/mail/mail-folder.c`, `revolution_mail_folder_mark_special`). Gmail-„Gesendet“ bleibt ein normaler Ordner wie in Evolution (EDS lässt ihn in der Ersteinrichtung aus, camel-imapx-store.c:2874-2881). Ungelesen-Zähler rechts in der Ordnerzeile: microsoft365 aus der Ordnerliste (Graph), imapx erst nach dem Abgleich in dieser Sitzung (Posteingänge beim Start, geöffnete Ordner), danach live über `CamelFolder::changed`; Begründung bei `forget_unread` in `src/main.c`. Log: `Spezialordner: <UID> <Typ> <Ordner> (ESource|Ersteinrichtung)`, `Ungelesen: <UID> <Ordner> <N>`, `Erstauswahl: …`. Unabhängiger Vergleich, nur lesend (IMAP STATUS, Graph GET): `tests/testdaten.py --zaehler LOG`. Beim Start wird der zuletzt gewählte Ordner gewählt (GSettings `selected-folder`), sonst der Posteingang des ersten Kontos; `REVOLUTION_FOLDER` hat Vorrang. Einstellungen über mehrere Starts im Test: `GSETTINGS_BACKEND=keyfile XDG_CONFIG_HOME=<Ordner> scripts/screenshot.sh …`.

## Git-Hook

`hooks/pre-merge-commit` baut und testet das Merge-Ergebnis in `build-hook-devel/` mit `profile=development` und `werror=true` (#439) (`meson compile` und `meson test --no-suite smoke`, also offline ohne den Smoke-Test); jede Compiler-Warnung zählt also als Fehler. Schlägt eins davon fehl, bricht `git merge` ohne Commit ab. Der Merge bleibt dann offen und wird mit `git merge --abort` zurückgenommen. Einmal je Klon aktivieren:

```sh
git config core.hooksPath hooks
git config merge.ff false
```

Lücken: Der Hook läuft nicht bei `git merge --no-verify` und nicht, wenn der Merge mit Konflikt stoppt. Den Konflikt-Commit dann vor dem Abschluss selbst mit `meson configure -Dprofile=development -Dwerror=true build-hook-devel && meson compile -C build-hook-devel && meson test -C build-hook-devel --no-suite smoke` prüfen.

Arbeitsweise: ein Branch pro Task (`task/<Nr>-<kurz>`), Merge nach `main` erst nach dem Review.
